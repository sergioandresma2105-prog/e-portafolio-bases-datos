PL/SQL: control, funciones, procedimientos, triggers y paquetes

Construí lógica dentro de la base de datos con Oracle 19c, desde un bloque anónimo hasta paquetes completos con pruebas automáticas.

IF / CASELOOP · WHILE · FORCursoresExcepcionesFuncionesProcedimientosTriggersPaquetesBULK COLLECT / FORALLAUTONOMOUS_TRANSACTION

Lo que demostré

  • Sentencias de control: Usé IF, ELSIF y CASE (simple y buscado); comprobé que = NULL nunca es verdadero y que una sentencia CASE sin ELSE lanza CASE_NOT_FOUND. Recorrí datos con LOOP, WHILE, FOR, FOR sobre cursor, CONTINUE y EXIT con etiquetas, y comparé fila a fila contra BULK COLLECT + FORALL.
  • Funciones: Creé fn_nota_definitiva y la invoqué desde SQL, desde PL/SQL y contra DUAL. Provoqué y corregí PLS-00103, ORA-06503 (ruta sin RETURN) y ORA-14551 (DML en una función usada en SQL). Usé DETERMINISTIC con un índice basado en función, RESULT_CACHE y PRAGMA UDF.
  • Procedimientos: Escribí pr_registrar_matricula con parámetros IN/OUT/IN OUT, validaciones con RAISE_APPLICATION_ERROR, SELECT ... FOR UPDATE para controlar el cupo entre dos sesiones, SAVEPOINT y un log con transacción autónoma que sobrevive al ROLLBACK.
  • Disparadores: Implementé BEFORE/AFTER de fila y de sentencia, auditoría con INSERTING/UPDATING/DELETING, cláusula WHEN, FOLLOWS, INSTEAD OF sobre una vista, un trigger de DDL sobre el esquema, y resolví la tabla mutante (ORA-04091) con un disparador compuesto.
  • Paquetes: Desarrollé pkg_inventario (especificación y cuerpo, subprogramas privados, sobrecarga, constantes, catálogo de excepciones, estado e inicialización de sesión) y lo validé con un paquete de pruebas propio: 17 casos que imprimen [OK] o [FALLA].
Ver fragmento de código
-- Disparador compuesto: evita ORA-04091 al validar el cupo
CREATE OR REPLACE TRIGGER trg_tope_cupo
FOR INSERT ON trg_inscripcion
COMPOUND TRIGGER
  TYPE t_asignaturas IS TABLE OF NUMBER INDEX BY PLS_INTEGER;
  v_afectadas t_asignaturas;

  AFTER EACH ROW IS
  BEGIN
    v_afectadas(:NEW.id_asignatura) := 1;   -- solo recolecta
  END AFTER EACH ROW;

  AFTER STATEMENT IS
    v_idx PLS_INTEGER; v_total NUMBER; v_max NUMBER;
  BEGIN
    v_idx := v_afectadas.FIRST;
    WHILE v_idx IS NOT NULL LOOP
      SELECT COUNT(*) INTO v_total FROM trg_inscripcion WHERE id_asignatura = v_idx;
      SELECT cupo_maximo INTO v_max FROM trg_asignatura WHERE id_asignatura = v_idx;
      IF v_total > v_max THEN
        RAISE_APPLICATION_ERROR(-20031, 'Cupo excedido en la asignatura ' || v_idx);
      END IF;
      v_idx := v_afectadas.NEXT(v_idx);
    END LOOP;
  END AFTER STATEMENT;
END trg_tope_cupo;

EVIDENCIA 05

SQL avanzado — Quiz 2 AeroAndes

Con el esquema de una aerolínea (aeropuertos, vuelos, reservas, pasajeros e incidencias) analicé y corregí consultas defectuosas.

JOINSubconsultasNOT IN vs NOT EXISTSCTE (WITH)Funciones analíticasRANGE vs ROWSFan-out del join

Lo que demostré

Detecté por qué un NOT IN falla cuando la subconsulta trae NULL (columna de referidos) y lo corregí con NOT EXISTS; resolví la multiplicación de filas al unir vuelos con varias incidencias agregando antes del join; y expliqué la diferencia entre ventanas RANGE y ROWS cuando varias filas comparten la misma fecha.

Ver fragmento de código
-- NOT IN devuelve 0 filas si la subconsulta trae un NULL.
-- Corrección con NOT EXISTS:
SELECT p.id_pasajero, p.nombre
  FROM pasajero p
 WHERE NOT EXISTS (SELECT 1
                     FROM pasajero r
                    WHERE r.id_pasajero_referido = p.id_pasajero);

-- Evitar el fan-out: agregar incidencias antes del join
WITH inc AS (SELECT id_vuelo, SUM(minutos_retraso) AS retraso
               FROM incidencia GROUP BY id_vuelo)
SELECT v.num_vuelo, SUM(r.tarifa) AS ingreso, MAX(inc.retraso) AS retraso
  FROM vuelo v
  JOIN reserva r ON r.id_vuelo = v.id_vuelo
  LEFT JOIN inc  ON inc.id_vuelo = v.id_vuelo
 GROUP BY v.num_vuelo;
